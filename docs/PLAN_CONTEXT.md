## 1. Project

**TrustLedger** — fair, private, explainable credit scoring for people without a credit history in Bangladesh.

- Event: International AI Builders Congress 2026 — problem **CreditForAll** (FinSphere AI track)
- Final: **26 December 2026**, Daffodil International University, Ashulia, Dhaka
- Code freeze: **23 December 2026** (only bug fixes after this)
- Team: Team Minus One
  - Dipanwita Maitra — Team Lead, Voiceover & Scripting
  - Prayangshu Biswas — Video Editor, Co-Developer & AI/ML Engineer
  - Daniel — Lead Developer
  - Soniya — Researcher & UI/UX
  - Fariha — Documentation & Co-Research

**One-liner:** TrustLedger turns everyday phone habits into a fair, private and explainable credit score, so no responsible Bangladeshi is rejected just for being invisible to banks.

**Target users:** students, gig workers, garment workers, homemakers, young professionals — anyone with a phone but no bank credit history. Demo persona: **Moon**, 24, garment worker in Ashulia, no bank account, no salary slip, pays every bill on time.

**Brief requirements we must visibly meet:** ML scoring + explainable decisions + bias controls, with fair, inclusive approvals and *measurable reach*.

## 2. What already exists (do not redo)

| Path | What it is |
|---|---|
| `trustLedger_model_training.ipynb` | Trains all models. Sections: Findex, Home Credit, LendingClub, synthetic Bangladesh model, SHAP, fairness, inclusion lift, federated, save |
| `models/trustledger_xgb.json` | **Production model** (XGBoost, predicts P(repay)) |
| `models/trustledger_meta.json` | `features`, `threshold`, `group_thresholds`, `score_scale`, `reasons` (Bangla good/bad), `tips` (Bangla) |
| `models/federated_weights.npy` | FedAvg logistic weights (simulation) |
| `models/homecredit_alt_xgb.json`, `homecredit_meta.json`, `lendingclub_xgb.json` | Real-data validation models (not used in production) |
| `training_files/*.png`, `training_files/metrics.json` | Figures and metrics used in README, docs and pitch |
| `datasets/` | Raw data (Git LFS). `trustledger_synthetic_bd.csv` is generated by the notebook |
| `pyproject.toml`, `uv` | Python 3.12, managed with uv |

**Model contract (must match the notebook exactly):**

```
FEATURES = [
  "monthly_inflow_bdt", "income_volatility", "months_on_wallet", "txn_per_month",
  "bills_on_time", "recharge_regularity", "savings_ratio", "sends_money_home",
  "bhorsha_score", "loan_to_income"
]
```

- Missing values are allowed (`NaN`) — zero-history users have no wallet features and rely on `bhorsha_score`.
- Output: `p_repay` in [0, 1]. Score: `600 + 50/ln(2) * ln((p/(1-p))/4)`, clipped to 300–900.
- Bands: ≥750 Excellent, ≥650 Good, ≥550 Fair, else Building.
- Decision: approve if `p_repay >= group_thresholds[group]`, where group ∈ `F_rural, F_urban, M_rural, M_urban`.
- Reasons: SHAP on the XGBoost model, ignore |impact| < 0.02 and missing features, top 2 good + top 2 bad, Bangla text from `trustledger_meta.json`.

If the model is retrained, only the files in `models/` change — code must read everything from `trustledger_meta.json`, never hard-code thresholds.

## 3. Architecture

```
Borrower app (Flutter) ─┐
Lender dashboard (React)┼─► FastAPI backend ─► LangGraph agents ─► scoring core (XGBoost + SHAP + fairness)
Partner AI agents ──────┘        │                    │
        (MCP)                    │                    ├─ Data Agent: SMS parser + DeepSeek-OCR → features
                                 │                    ├─ Bhorsha Agent: Bangla psychometric chat → bhorsha_score
                                 │                    ├─ Explainer Agent: SHAP + RAG → Bangla reasons/tips
                                 │                    └─ Fairness Agent: group thresholds + audit log
                                 ├─ PostgreSQL + pgvector, Redis, Cloudflare R2
                                 ├─ Temporal (loan lifecycle), Airflow (weekly audits, drift, FL rounds)
                                 └─ Flower (federated learning)
```

**Agent order:** Data → (no history? → Bhorsha) → Scoring → Explainer → Fairness → decision. Nothing is approved until the Fairness Agent signs off.

## 6. Non-negotiable rules

**Fairness**
- `gender`, `region`, `division`, `age` are **never** model inputs. They are used only by the Fairness Agent for thresholds and audits.
- Every decision is logged with model version, features, SHAP reasons, group, threshold used and fairness result.
- Approval-rate gap and equalized-odds gap between groups must stay ≤ 0.05 on the test set; CI fails if they don't.

**Privacy**
- Raw SMS never leaves the device in production. On the server only derived features are stored. (In the demo, raw SMS may be sent to the API only when `DEMO_MODE=true`, and is never persisted.)
- PII is redacted with Presidio before any external LLM call.
- Every data source needs a consent record. `DELETE /me` removes all user data.
- No real personal data in the repo, tests or fixtures — synthetic only.

**Explainability**
- Every score response includes Bangla reasons and tips. No score without reasons.
- The Explainer may only mention features that actually appear in the SHAP output.

**Reliability**
- Every LLM call goes through `LLMClient`, has a timeout, retries, schema validation, and a mock implementation so tests run offline with no API keys.
- Secrets only from environment variables. `.env.example` lists every variable; `.env` is git-ignored.

**Branding**
- No real bank, bKash or Nagad logos in the UI. Text mentions of "bKash/Nagad" are fine.

## 7. Coding conventions

- Small, readable modules. Type hints everywhere. Docstrings only where the *why* isn't obvious.
- Plain comments, no emojis in code, no long AI-style explanations.
- Pure functions in `core/` — no network, no DB.
- Each feature lands with tests. Target ≥ 80% coverage for `backend/app/core` and `parsers`.
- `ruff check`, `ruff format`, `mypy backend/app` and `pytest` must pass before a prompt is done.
- Bangla strings live in data files (JSON/YAML), not scattered in code.

**Environment variables (add to `.env.example` as they appear)**
`DATABASE_URL`, `REDIS_URL`, `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL`, `DEEPSEEK_OCR_URL`, `LLM_MODE` (`mock` | `live`), `R2_ENDPOINT`, `R2_ACCESS_KEY`, `R2_SECRET_KEY`, `R2_BUCKET`, `API_KEYS`, `DEMO_MODE`, `TEMPORAL_HOST`, `MODEL_DIR`.

## 8. How every prompt is run

1. Read `PLAN_CONTEXT.md` fully.
2. Read `PROMPT.md` and every existing `docs/PROMPT*_REPORT.md` to know the current state.
3. Do **only** the scope of the current prompt. If something earlier is broken, fix it minimally and say so in the report.
4. Run lint, type checks and tests. Fix failures.
5. Write the report `docs/PROMPT{N}_REPORT.md` using the template below.
6. Tick the prompt in `PROMPT.md` (`- [ ]` → `- [x]`).
7. Commit once: `prompt {NN}: {short title}`.

If blocked (missing key, missing data, unclear requirement): do everything possible with mocks, mark the item **BLOCKED** in the report with what is needed, and still tick the prompt only if all acceptance criteria that don't depend on the blocker pass.
